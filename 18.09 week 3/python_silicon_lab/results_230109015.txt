========================================================================
 54           RESUME                   0

              LOAD_ATTR                0 (val)

              BINARY_OP               13 (+=)
              SWAP                     2
              STORE_ATTR               0 (val)
              LOAD_CONST               1 (None)
              RETURN_VALUE

Read the sequence: the value is loaded by LOAD_ATTR, incremented by
BINARY_OP, and written back by STORE_ATTR. Between the load and the
store there is no CALL, no backward jump and no RESUME - and those
are precisely the instructions at which CPython tests its eval_breaker
and may release the GIL. The window in which another thread could
read a stale value is therefore never opened by this code.

Contrast - the instrumented variant:
 69           RESUME                   0
              LOAD_FAST_BORROW         0 (self)
              LOAD_ATTR                0 (val)
              LOAD_GLOBAL              3 (_addend + NULL)
              CALL                     0
              BINARY_OP                0 (+)
              LOAD_FAST_BORROW         0 (self)
              STORE_ATTR               0 (val)
              LOAD_CONST               0 (None)
              RETURN_VALUE

Here a CALL (and the callee's RESUME) sits between the load of
self.val and the STORE_ATTR that writes it back. That is a legal
GIL hand-off point inside the read-modify-write sequence.
